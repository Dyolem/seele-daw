# Seele DAW 长期架构与路线

本文回答三件事：现在的架构到了什么程度，要长成什么样，按什么顺序走。

- 代码现在的样子见 [ARCHITECTURE](../../ARCHITECTURE.md)，已经做出的决定见 [ADR](../adr/README.md)，
  产品现状见 [PRODUCT](../../PRODUCT.md)。本文与它们冲突时以它们为准。
- 除第 1 节的评估外，本文只写还没实现的方向。一个方向落地后，把结论写进 ARCHITECTURE 和 ADR，
  并从本文删掉；第 1 节在每个阶段结束时重新评估。
- 本文取代 [长期路线 v3](../archive/architecture/web-daw-long-term-architecture-v3.md)。v3 里
  Audio Clip、资产提交协议、录音与离线导出的详细草案仍可参考，但对应阶段开工时要重新确认：
  它写在 2026-10 的重构之前，有些前提已经变了（例如 ADR-004 与 ADR-005）。

## 1. 现状评估（2026-11）

评估依据：全仓生产代码的导入图（包之间、包内目录之间、文件级循环），代码量与最大文件统计，
以及对模型、播放管线和持久化的逐项核对。

### 1.1 结论

底座已经可以长期维护：包的分层、项目内核和提交管线是稳固的，往里加同类的东西（命令、实体表、
Action、手势、订阅者）有固定配方，漏了什么由类型检查指出。

但整体还不能说已经是可扩展的形态。产品接下来要做的混音、合成器、Automation 和音频，走的都是
目前最窄的几处：播放与音频是专为“MIDI 音符 → 采样 Voice”写的，Device 只有描述没有定义，
Studio 内部的层次靠约定并且已有违反，数据安全与自动化门禁也还没有。

| 维度              | 判断     | 依据                                                                                                                           |
| ----------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 包之间的层次      | 达标     | 依赖图无环，方向与 ARCHITECTURE 的表一致，`pnpm lint` 检查，零违规；核心包的 tsconfig 不含 DOM 类型                            |
| 包之间的耦合      | 达标     | 消费者只读 Commit 里的存储变化（ADR-002、ADR-004）；audio-web 只实现 playback 的一个端口；平台实现都由 Studio 注入             |
| 项目内核          | 达标     | 一份事实、一条提交管线；表与命令注册表是声明式的；提交、Snapshot、编译的成本随改动增长（ADR-007 至 ADR-010）；458 个测试       |
| MIDI 领域模型     | 达标     | Track、Clip、Source、Note、踏板、Tempo、拍号的身份、时间与不变量清楚                                                           |
| 模型里的空转部分  | 未达标   | Audio Track、效果链、Clip Loop 有记录、不变量和文件格式，却没有界面创建，播放只把它们报告为不支持                              |
| Device            | 未达标   | 只有通用的 `DeviceDescriptor`；唯一的设备类型写死在 playback 的编译器里，目录与路由在 Studio，没有 Device Definition           |
| 播放与音频的扩展  | 未达标   | 计划类型与运行时端口按采样 Voice 命名和成形；Track 的 Gain / Pan 在排程时乘进每个 Voice，没有常驻的通道节点                    |
| 编辑器的扩展      | 部分达标 | 输入与手势内核是通用的；但只有 Piano Roll 的几何在 editor 包里，Arrangement 与 Tempo Lane 的几何在 Studio 的组件里，且没有缩放 |
| Studio 内部的层次 | 未达标   | 方向靠约定，工具不检查；一个 14 个文件的导入循环，两个 feature 互相导入，workbench 引用了 bootstrap 的类型                     |
| 数据安全          | 未达标   | 只有显式保存；没有自动保存、关闭页面保护和多标签页协调                                                                         |
| 自动化门禁        | 未达标   | `pnpm check` 只在本机手动运行；没有 CI，没有浏览器端到端测试；音质报告要手动打开页面看                                         |

### 1.2 已经稳固的部分

下面这些是往后所有工作的地基，除非 ADR 的重新评估条件被触发，否则不再改动。

- **包图**：`type-utils`、`midi-file` 是叶子；`project-core` 只依赖类型工具；`editor`、`playback`、
  `project-midi`、`platform-browser` 依赖 core；`audio-web` 只依赖 playback；Studio 是唯一组合根。
- **提交管线**：命令由工厂创建并校验，按类型分发到 handler，产出可逆的计划；提交只校验它写过的
  内容，回滚失败会锁死写入；Undo / Redo 走同一条管线。
- **存储**：表声明一次，存储、投影、变化与项目文件都按声明编写；Snapshot 与文件同形；没变的记录
  在 revision 之间是同一个对象，下游按身份复用。
- **边界上的检查**：外部数据在文件、存储、浏览器 API 和注入的回调处解析一次，内部信任类型。
  错误只在调用方会分支或命名领域规则时带 code。
- **订阅协议**：订阅者是函数，抛错只报告、不回送、不退订。
- **交互内核**：Pointer 输入归一化，一次手势只提交一次，遇到别人的提交或 Surface 移动即取消。

### 1.3 还不成立的部分

这些是路线里要解决的问题，编号在第 4 节引用。

1. **Studio 内部没有被检查的层次。** `workbench/actions/studio-actions.ts` 导入三个 feature 的
   Action 声明，而 feature 又导入 workbench 的 `defineStudioAction`，形成 14 个文件的循环；
   `features/piano-roll` 与 `features/project-workspace` 互相导入（时间轴刻度、选择 Store 与
   Piano Roll 组件）；`workbench` 有两处引用 `bootstrap` 里的类型。
2. **模型里有空转的事实。** Audio Track 没有命令能创建；效果链数组永远为空；Clip Loop 能随
   Add Clip 命令写入，但没有界面使用，编辑与播放都拒绝它。它们让不变量、解码器、诊断码和
   测试夹具为不存在的功能付出成本。
3. **Device 没有定义层。** 设备的参数、状态解码和能力没有统一的声明；`SampleInstrument` 的知识
   分散在 playback（定义与状态解码）、audio-web（Manifest 与 Voice）和 Studio（目录与路由）。
   目录里 150 个合成器 Preset 还不能发声；要接入它们的引擎，先得有这一层。
4. **播放管线是单一用途的。** `TrackPlaybackPlan.instrument` 只有一种；端口的 `schedule` 只接收
   采样 Voice；没有常驻的通道图，所以推子、Mute 的实时生效、效果器和电平表都无处安放。
5. **编排的几何不在 editor 包里。** Arrangement 是固定刻度的 DOM 布局；时间轴的 Tick 与像素换算
   在 Studio 的一个 feature 里，被另一个 feature 跨界导入。
6. **数据安全只有显式保存。** 刷新或关闭页面会丢掉未保存的工作；两个标签页可以同时写同一个
   项目；恢复到较旧的 Checkpoint 时用户不知道。
7. **门禁要人来跑。** 没有 CI；核心流程（新建、画音符、播放、保存、刷新恢复）只有手动验证；
   内置音色的人工听测状态仍是 `not-run`。
8. **几个文件过大。** `playback-engine.ts` 1,051 行，`ProjectEntryPage.vue` 959 行，
   `ProjectWorkbenchArrangement.vue` 820 行。它们各自内聚，但下一次要改时应先按职责拆开。
9. **公开构建没有声音。** 采样资产是开发者本机文件，生产构建不带；这是产品与许可问题，也是
   发布的前提。

## 2. 不变的规则

后面每个阶段都要守住这些规则。它们来自 v3 的原则和 2026-10 的重构，已经由代码验证过。

1. **项目事实只有一份。** 可保存、可撤销的事实在 `ProjectSession` 里，只能通过命令修改。
2. **运行时可以重建。** AudioNode、Voice、解码后的 PCM、播放计划、索引和 Read Model 都不进入
   项目文件，丢掉之后能从事实重新得到。
3. **一次用户动作是一次原子提交。** 它只增加一次 revision、只产生一个 History 步骤；磁盘和
   音频的副作用发生在提交之后，失败不回滚已经合法的事实。
4. **消费者读变化，不读命令类型。** 新命令不应要求播放、界面或持久化跟着改。
5. **检查只放在边界。** 值从文件、存储、浏览器 API 或注入的回调进来时解析一次；之后信任类型。
6. **核心不依赖平台。** project-core、playback、midi-file、project-midi 不碰 DOM、Web Audio、
   IndexedDB 和 Vue；平台实现由组合根注入。
7. **模型不留空转的事实。** 一个概念进入模型，要同时有命令创建它、有消费者解释它，并写清它的
   不变量按什么规模检查（ADR-008）。
8. **音乐时间与音频时钟分开。** Tick 是整数，PPQ 固定为 960；秒只出现在编译与运行时的边界；
   声音何时开始只看音频时钟，不看定时器。
9. **成本随改动增长。** 新的派生数据沿用同一办法：按 Clip 或分区保存，按对象身份复用。
10. **降级必须显式。** 能力不足、设备缺失或资源加载失败时，禁用并说明原因，不静默换一种声音。
11. **抽象等第二个实例。** 通用的图、注册表、Worker 协议都在第二个真实需求出现时再提取；
    第 3 节写明每一个的触发条件。
12. **缓存与资产分开对待。** 可重建的缓存可以随时删除；用户的原始资产只能保守地删除。

## 3. 目标架构

### 3.1 包与层

包图保持不变。新建一个包要同时满足：依赖方向清楚、能脱离应用单独测试、至少有两个上层消费者
或者必须隔离一个平台或第三方实现、拆出来不会产生成对的转换类型。

要补上的是包内部的方向：

- **Studio**：`ui` ← `workbench` ← `features` ← `bootstrap`、`router`、`App`，右边可以导入
  左边，反过来不行。workbench 不导入 feature 和 bootstrap；feature 之间只能单向依赖，外壳可以组合被嵌入的 feature，反过来不行；
  多个 feature 共用的状态与几何下沉到 workbench 或 editor 包。
- **全仓**：生产代码没有文件级的导入循环。
- **project-core**（指导性，不入规则）：基础值（ID、标量、Tick、JSON）← 记录 ← mutation ←
  commands ← commit、history ← session；snapshots、queries、subscriptions 是读侧；persistence
  在最上层。

前两条写进 `tooling/architecture-rules`。规则仍然只检查方向与循环，不规定目录的形状。

### 3.2 领域模型

| 概念       | 现状                                   | 目标                                                               | 触发                 |
| ---------- | -------------------------------------- | ------------------------------------------------------------------ | -------------------- |
| Track      | 只有 Instrument 可用                   | 用 `source` 区分 Instrument 与 Audio，不按乐器种类建子类           | Audio 阶段           |
| Channel    | Gain、Pan、Mute、Solo 有事实，没有命令 | 有命令；运行时是常驻通道，改参数不重启 Voice                       | 阶段 1               |
| Clip       | 只有 MIDI Clip                         | 加 Audio Clip；移动、拆分等编排操作对两种 Clip 语义一致            | 阶段 1、Audio 阶段   |
| Device     | 通用 Descriptor，加一种写死的类型      | Descriptor 不变；类型知识集中在 Device Definition                  | 第二种设备           |
| Automation | 没有                                   | `ParameterAddress`（Track 参数或 Device 参数）加按 Lane 分区的点表 | Device Definition 后 |
| Asset      | 没有                                   | `AssetId` 是项目引用，内容哈希是存储身份                           | Audio 阶段           |
| 拍号       | 有事件表，只读                         | 有编辑命令                                                         | 产品需要时           |

下面几条语义 v3 已经论证过，到时直接沿用，开工时在 ADR 里确认：

- **Audio Clip 只有一个权威长度。** 起点按 Tick，素材区间按整数微秒，原速播放；时间线上的终点
  由 Tempo Map 推导。Warp 与变调以后作为新的播放模式加入，不让固定模式同时保存秒和 Tick 两个
  长度。素材区间用媒体时间而不是解码后的采样下标，因为解码会重采样。
- **MIDI Source 只有一个 Clip 所有者**（现在已是不变量）。复制 Clip 时复制 Source 并生成新
  ID；Linked Clip 是独立功能，不能由共享引用意外产生。
- **Automation 的值按参数定义归一化。** 连续参数保存 0 到 1 的值，映射由 Device Definition
  负责；离散参数只能阶跃。
- **缺失的设备原样保留。** 找不到实现时保留 Descriptor 与状态，界面显示 Missing，保存时不丢。

Device Definition 的归属：项目文件里的 `DeviceDescriptor` 留在 project-core，core 不认识具体
设备类型；与浏览器无关的定义（类型 ID、版本、角色、参数表、状态解码、能否离线渲染、延迟与
尾音）放在 playback；把定义映射到 Web Audio 实现的适配器放在 audio-web；Preset 目录与资产地址
留在 Studio。参数值的语义校验由定义所在的一层完成，不合法的值变成诊断和 Missing 状态，而不是
被 core 拒绝提交。这一条在动手前写成 ADR。

### 3.3 播放与音频

现在的管线是 Snapshot → 按 Clip 编译音符 → 调和 → 按窗口排程 → 端口 `prepare` /
`schedule(voice)`。它要分四步变宽，每一步都由一个具体功能触发，不提前做。

1. **常驻通道图**（触发：Track 的 Mute、Solo、Gain、Pan 可以编辑）。audio-web 为每个 Track 维护
   一条通道：输入 → 增益 → 声像 → Master。Voice 接到所属 Track 的输入，自己只管力度与包络。
   计划里已经有每个 Track 的通道参数；端口新增“按计划对齐通道”这一步。参数变化用短斜坡，
   不重启 Voice。效果器和电平表以后都挂在这条通道上。
2. **Device 注册表**（触发：第二种乐器或第一个效果器）。编译器向注册表询问设备的计划，不再
   认识具体类型；计划里的乐器成为按运行时种类区分的联合；audio-web 按种类找适配器。
   `AudibleMidi*` 这批名字在这一步改掉。
3. **更多种类的事件，以及 AudioWorklet**（触发：合成器 DSP，或需要采样精确的参数变化）。事件
   带目标时间和 generation，过期的直接丢弃；Worklet 不读项目对象、不解析 JSON、不在处理回调里
   分配内存。SharedArrayBuffer 只是优化，不能成为正确性的前提。能力探测随第一个可选能力一起
   引入。
4. **离线渲染**（触发：WAV 导出）。编译与排程与浏览器无关，可以不靠定时器一次排完整个范围；
   要新写的是离线驱动和编码。每个设备声明自己能否离线渲染，不能时导出要明确提示。

这四步里不变的是：编译产物与浏览器无关，audio-web 不读项目；整个应用一个输出（ADR-006）；
计划按 Clip 保存、按身份复用（ADR-009、ADR-010）；第三方音频库只能藏在某个设备适配器后面。

### 3.4 编辑器

editor 包应当拥有每一个编辑 Surface 的输入归一化、手势、几何、命中测试、操作、Read Model 和
Canvas 渲染；Studio 只保留 Vue 组件、把意图接到 `edits` 的胶水，以及产品默认值。

- 时间轴视口（Tick 与像素的换算、缩放、吸附）是 Arrangement、Tempo Lane 和 Piano Roll 的
  Track Surface 共用的，进 `editor/common`，只有一个实现。
- Arrangement 获得缩放和 Clip 编辑时，Clip 的几何、命中和操作按 `InteractionOperation` 写进
  `editor/common`，与 Piano Roll 的音符操作同构。
- Selection 只保存稳定身份，切换项目时清空，提交后清理失效的引用。Clipboard 的载荷与原项目
  ID 无关；粘贴时生成新 ID，并作为一条命令提交。

### 3.5 持久化与数据安全

按下面的顺序加，每一步都比前一步多一点机制。

1. **关闭页面保护与自动保存。** 自动保存先用防抖的 Checkpoint 实现，写入单独的恢复点，不覆盖
   用户显式保存的那一份。先测大项目上一次 Checkpoint 的耗时，在预算内就不需要 Journal。
2. **多标签页。** 用 Web Locks 保证一个项目同一时刻只有一个写者。
3. **项目文件导出与导入。** 先是不含资产的项目文件，Audio 阶段之后是带资产的项目包。
4. **迁移。** 现在只读当前格式（ADR-005）。从第一份真实用户数据出现的那天起，每次
   `formatVersion` 变化都要带一个 JSON 到 JSON 的迁移函数和一份旧文件夹具。这是公开发布的门槛。
5. **资产库。** IndexedDB 与 OPFS 不能一起原子提交，所以先把 Blob 写完整并校验，再在一次
   IndexedDB 事务里提交对它的引用；项目永远不引用未完成的 Blob。清理用标记清除，不只靠引用
   计数。
6. **Journal。** 只有当 Checkpoint 的成本被测出是问题时才引入。

### 3.6 质量门禁

- CI 在每次推送时运行 `pnpm check`。
- 一条浏览器冒烟测试覆盖核心流程：新建项目、加 Track、画音符、播放、保存、刷新后恢复。
- 架构规则增加 3.1 的两条。
- 性能预算（第 7 节）在每个阶段结束时复测，结果写进对应的 ADR。
- 声音：AQ0 的合成 PCM 报告改成可以脚本运行的检查；改变听感的变更仍需要人工听测。

## 4. 路线

阶段按依赖排列，顺序是建议；哪些先做由项目负责人决定（见第 5 节）。每个阶段开工前，把其中标了
ADR 的决定写成 ADR。

```text
阶段 0 收口 → 阶段 1 编排与混音 → 阶段 3 Device 与合成器 → 阶段 4 Automation
              阶段 1 → 阶段 5 Audio
              阶段 3 与阶段 5 → 阶段 6 录音
阶段 2 数据安全与交付：与阶段 1 互不依赖，可以穿插
阶段 7 云端：在阶段 2 与阶段 5 之后
```

### 阶段 0：收口

不加功能，解决 1.3 里已经清楚该怎么做的问题。

- Studio 层次（1.3-1）：Action 的汇总移到组合层，workbench 只提供声明、注册与分发的机制；
  时间轴刻度与工作台选择 Store 下沉，Piano Roll 不再导入 Project Workspace；`StudioActionRuntime`
  的类型归到 workbench。然后把 3.1 的两条规则写进工具。
- 模型去空转（1.3-2）：Audio Track、效果链与 Clip Loop 要么接通，要么删除。建议删除，到对应
  阶段带着真实语义重新加入；现在没有需要兼容的数据。这一项等第 5 节第 2 条的决定。
- 包内整理：project-core 里 `time` 与 `model` 互相导入，`history` 引用 `session` 的类型，把基础值
  与内容状态 ID 放回各自该在的一层；playback 的设备定义离开包根目录。
- 门禁（1.3-7）：CI 与一条浏览器冒烟测试。

完成标准：架构规则检查 Studio 层次与文件级循环并且零违规；CI 通过；模型里每张表、每个字段
都有命令写入和消费者读取。

### 阶段 1：编排与混音可编辑

目标是把 MIDI 创作闭环补完整：Clip 的移动、调整长度、拆分、删除、复制与多选；Track 的重命名、
改色、删除、复制与重排；Mute、Solo、Gain、Pan；Velocity 编辑；Arrangement 的缩放与吸附。

- 命令按 ARCHITECTURE 的配方添加，是纯增量。Move、Resize、Split 的产品边界先定。
- 常驻通道图（3.3 第 1 步，ADR）。
- 时间轴视口与 Arrangement 的几何、操作进 editor 包（3.4）；届时拆分
  `ProjectWorkbenchArrangement.vue`。
- Selection 扩展到 Clip 多选；Clipboard 载荷。
- 通道图会改到 `playback-engine.ts`；动手前先把定位、提交交接和调度循环拆成各自的对象。

完成标准：播放中拖动推子不重启正在响的 Voice；Arrangement 的每种编辑都是一次手势一次提交；
1,000 个 Clip、32 条 Track 的项目上，编辑与滚动在预算内。

### 阶段 2：数据安全与交付

目标是让用户敢把作品放在里面，并且能拿出去：自动保存与恢复点、关闭页面保护、多标签页保护、
项目文件导出导入、项目重命名与删除、Standard MIDI File 导出、WAV 导出、可分发的音源。

- 3.5 的第 1 至 4 步；迁移机制在公开发布前就位。
- 离线渲染（3.3 第 4 步，ADR）。如果排在阶段 3 之后，导出就能覆盖合成器。
- 恢复到较旧的 Checkpoint 时告知用户。

完成标准：崩溃或刷新后丢失的工作不超过自动保存的间隔；第二个标签页不能写同一个项目；导出的
WAV 与实时播放在 AQ0 的指标上一致；每一步存储操作失败都有注入测试。

### 阶段 3：Device 与合成器

目标是让目录里的合成器 Preset 发声，并提供基础效果器和电平表。

- Device Definition 与注册表（3.2、3.3 第 2 步，ADR）。
- 第一个自研 DSP 带来 AudioWorklet、它的消息协议和能力探测（3.3 第 3 步，ADR）。
- 效果链带着真实语义回到模型：串联顺序、旁通、缺失设备。
- 没有延迟补偿之前，只接受零延迟或固定已知延迟的设备。

完成标准：新增一种设备只需要写定义和适配器，编译器、调和与端口不改；每个设备通过同一套
契约测试；缺失设备的项目能打开、能保存、不丢状态。

### 阶段 4：Automation

目标是 Track 与 Device 参数的自动化曲线。依赖阶段 1 的通道图和阶段 3 的参数表。

- `ParameterAddress`、Lane 与点表（按 Lane 分区，沿用内容表的不变量规则）。
- 编译成参数斜坡；播放中编辑曲线只影响未来的片段。
- Lane 的几何与操作进 editor 包。

### 阶段 5：Audio

目标是导入音频、在 Arrangement 中裁剪、移动和拆分，并看到波形。依赖阶段 1 的通道图。

- 资产库与引用提交协议（3.5 第 5 步，ADR）；导入管线：临时文件、校验、哈希、探测元数据、
  完成 Blob，最后才提交“加资产并加 Clip”的命令。
- Audio Clip 的时间语义（3.2，ADR）；Tempo 改变后的行为要有测试。
- 解码缓存与多分辨率波形峰值是可重建的缓存，在 Worker 里生成。
- 项目包：项目文件加按内容哈希命名的资产。

完成标准：项目永不引用未完成的资产；删除全部缓存后项目仍能完整打开；配额不足不损坏已有项目。

### 阶段 6：录音

依赖阶段 5 的资产库和阶段 3 的 AudioWorklet。正式录音走 Worklet 采集 PCM，写入待定文件，完成后
成为资产并以一条命令创建 Clip；MediaRecorder 不能作为正式的录音路径。权限拒绝、设备拔出、
配额耗尽、崩溃后的待定文件，以及延迟补偿，都要单独验收。

### 阶段 7：云端

在阶段 2 和阶段 5 之后。先做单机版本的云保存：按内容哈希上传资产，乐观并发，冲突时保留两份而
不是静默覆盖；再做分享、评论。实时协作要等命令、存储变化和云版本经过实际使用后重新设计，
不提前把模型换成 CRDT 类型。

## 5. 需要项目负责人决定的事

这些不是实现细节；不先定下来，会在编辑、播放和历史几处出现不一致。

1. **阶段的顺序**，尤其是阶段 3（合成器）与阶段 5（Audio）谁先，以及阶段 2 何时插入。
2. **模型里三处空转**（Audio Track、效果链、Clip Loop）是删除还是保留。
3. **自动保存的语义**：是单独的恢复点，还是取代显式保存；有了它之后 Discard 意味着什么。
4. **Mute 的语义**：是通道静音（解除后正在响的音符能听到），还是像现在这样不排程。
5. **Clip 编辑的边界**：同一条 Track 上的 Clip 能否重叠；拆分和缩短时，跨边界的音符怎么处理。
6. **循环**：Clip Loop 与 Transport Loop 是否进入阶段 1；循环边界上 Note Off 与下一轮 Note On
   的顺序。
7. **恢复提示**：打开项目时最新的 Checkpoint 损坏、回退到上一份，要不要告诉用户。
8. **可分发的音源**：用哪些资产，许可与托管方式。这是公开发布的前提。
9. **公开发布的时间**。它决定迁移机制何时从“以后再说”变成硬要求。
10. **Audio 阶段开工前**：同一条 Track 上重叠的 Audio Clip 是混音、覆盖还是交叉淡化；导出时
    遇到只能实时运行的设备怎么办；录音延迟补偿的默认策略。

## 6. 明确不做

以下能力不作为当前架构的驱动力。架构不堵死它们，但也不为它们预留模型。

- VST / AU 宿主、任意插件 SDK、插件延迟补偿。
- Warp、弹性音频、Comping 与 Take 管理、通用的内容 Lane。
- 实时多人协作。
- 视频、环绕声、移动端的完整编辑。
- 把 Tone.js 或其他第三方库当作 Transport、调度、混音或项目模型的核心。
